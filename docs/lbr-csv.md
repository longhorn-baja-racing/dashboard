# Opening firmware session exports (lbr-csv)

The vehicle DAQ writes `.LBR` logs to its SD card. The firmware's reference
decoder exports a log as CSV:

```sh
python3 dev/tools/lbr_decode.py csv 00000012.LBR   # in the firmware repository
```

Open the resulting `00000012.csv` with **File > Open**. The dashboard
recognizes the export by its header row and shows it in the session view.
Other CSV files keep opening in the table view.

To try it without a car, open `sample_data/lbr_demo_session.csv`: a 10 second,
synthetic session generated by `scripts/make_lbr_demo_csv.py` with real signal
names and rates, an unfitted sensor, a sensor fault, a logger queue overflow
and a node that started before time sync. Its values are made up.

The format is lbr-csv version 1, defined in the firmware's `docs/protocol.md`
("CSV export") and pinned by its `dev/tests/fixtures/session.csv`. A copy of
that fixture is in `tests/fixtures/lbr/` and is checked in CI.

## The session view

- **Signals (left):** every channel, grouped by node. Samples are listed first,
  then each node's `heartbeat` and `health` fields. Check a signal to plot it;
  the filter matches names, nodes and units. Signals with no valid data are
  greyed out; hover for counts and unavailable reasons.
- **Plot:** time on the Central's clock (seconds since Central boot). Discrete
  signals (states, flags, counts) are drawn as steps. Event, fault and loss
  markers are drawn as vertical lines. Move the mouse over the plot to read every plotted
  signal's value at that time below it.
- **Selected signals:** sample count, unavailable count by reason, minimum,
  maximum, last value and time span of each plotted signal.
- **Events:** events, faults, loss records, firmware text lines, commands and
  raw frames in time order. Double-click one to center the plot on it.
- **Session:** versions, configuration, integrity counters and warnings. The
  view switches to this tab when there is something to look at.

## Rules the view follows

These come from the protocol specification:

- **Unavailable is not zero.** An unavailable sample (empty value, reason such
  as `NOT_FITTED` or `SENSOR_FAULT`) is a gap in the plot and is counted with
  its reason. A real `nan` reading is kept separate from a missing one.
- **Node clocks stay separate.** Samples with `synced = 0` were taken before a
  node was synchronized and are on its own clock. They become their own
  channel, marked `(node clock)`, and cannot be plotted on the same time axis
  as Central-clock signals. Plot them on their own.
- **Exact time.** `t_s` is read as integer microseconds, so no float rounding
  is introduced. Rows are sorted per channel, not globally.
- **Raw values are kept.** Scaled units such as `deg*1e-7` are converted only
  for display (`deg`); the stored values are untouched.
- **Problems are shown, not hidden.** The Session tab warns about corrupt
  regions, skipped bytes, a truncated tail, an unchecked catalog, a missing END
  record, logger queue overflows, node-clock samples, a boot after a panic,
  watchdog or brownout reset, unexpected protocol versions, unit changes,
  unknown row kinds and malformed rows.
- **Unreadable files are refused clearly.** A file that is not lbr-csv, or is a
  different `lbr_csv_version`, is refused with a message. The previously
  opened data stays on screen.

## Limits

- Reading is single-pass and streaming, about 300k rows per second on a
  development laptop, with a progress dialog that can cancel. A 2 million row
  export took about 7 s with a peak of about 140 MB for the whole process.
- Up to 5000 rows of each diagnostic kind (text, commands, raw frames, unknown
  records) are listed; the rest are counted.
- All plotted signals share one value axis; multiple Y axes are #39.

## Not covered yet

- Reading `.LBR` binary logs directly (#30) and live USB or WiFi streams (#33).
- Using `catalog.json` for value types, descriptions and event code names. The
  CSV already carries names and units.
- Applying per-node mounting transforms from session metadata (#29).
- Mapping these channels onto the generic signal model (#18) once it lands.
  Channel IDs already follow its ID rules, for example `driver_input.brake_pedal`,
  `central.health.uptime_ms` and `stress.stress_3.node-clock`.
